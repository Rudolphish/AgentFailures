# 今後の改善案

着手していない案の置き場。判断の根拠と、いつ着手すべきかを添える。
実施したものは削除し、判断が変わったものは理由を書き添えて残す。

本書は**このリポジトリと、それを取り巻く仕組み**に関する案を扱う。
新しいサービスの構想はここには置かない。

---

## 0. 環境情報をユーザー設定へ書く（最優先・5 分）

`~/.claude/CLAUDE.md`（リポジトリではなくユーザー設定側）へ、開発環境を記載する。

```markdown
## 実行環境
- Windows / Windows PowerShell 5.1（`curl` は Invoke-WebRequest の別名）
- Git Bash 利用可。Unix 系のコマンドはこちらで実行できる
- Node.js 22 / openssl は無い
- `.ps1` は UTF-8 (BOM 付き) で保存すること
```

**根拠**: 2026-09-09 のセットアップで、環境差により 3 回作業が止まった
（`openssl` 不在 / `curl` の別名 / BOM 無し UTF-8 の読み取り）。
いずれも事前に環境が分かっていれば発生しなかった。

**効果の範囲**: 全プロジェクト・全セッション。リポジトリ側の `CLAUDE.md` と違い、
新しいリポジトリでも自動的に効く。

---

## 1. フック一式をプラグイン化する（推奨）

`.claude/hooks/` の自動レビュー機構を Claude Code のプラグインまたはスキルとして
切り出し、各リポジトリからは参照するだけにする。

**根拠**: 2026-09-10 時点で、同じフックが AgentFailures と gamers-highlight の
2 箇所に存在し、既に分岐している（`auto-review.mjs` で 18 行、
`review-status.mjs` と `session-brief.mjs` で各 2 行）。
AgentFailures 側にのみ加えた変更が、もう一方へ反映されていないためである。

あわせて `review-decisions.csv` の運用規約（開発側が書けるのは `accepted` のみ）も
AgentFailures の `CLAUDE.md` にしか無く、gamers-highlight 側には無い。

**着手すべき時期**: 早いほど安い。分岐が広がるほど統合の手間が増える。
以降の改善がすべて 2 箇所作業になるため、他の案より先に行う価値がある。

---

## 2. 自動レビューの FAIL を失敗談ストアへ流し込む

`auto-review.mjs` は FAIL のたびに「同じ失敗を繰り返さない項目を `docs/lessons.md`
か `CLAUDE.md` へ書け」と指示している。ここへ `record_failure` の呼び出しを加える。

**根拠**: 失敗談ストアの制約は機能ではなく件数である。人が思い出して記録する
運用は続かない。指摘が出た瞬間が、その学びが存在している唯一の時点である。

**注意**: レビューの指摘には新たな欠陥だけでなく設計上の好みも混ざる。
全件を流すとノイズで検索の質が落ちる。**FAIL のうち実際に修正コミットを
生んだものに限る**などの絞り込みを設けること。

---

## 3. 決定ログ（新規に作るならこれ）

「何を決めたか」と「どの条件で見直すか」を蓄積する。失敗談ストアと同じ骨格
（Cloudflare Workers + Supabase + ツール 2 つ）で作れる。

**根拠**: 2026-09-09 から 10 にかけて、以下の判断を行ったが、いずれも会話の履歴に
しか残っていない。新しいセッションのエージェントはこれを知らないため、
同じ議論を繰り返すか、決定に反する提案を行う。

| 決めたこと | 見直す条件 |
| --- | --- |
| `domain` は技術、`tags` は話題 | `nextjs` が肥大化したら細分化を検討 |
| `review-decisions.csv` へ開発側が書けるのは `accepted` のみ | — |
| 更新の権限分離は作らない | 追記では足りないと分かったら |
| pgvector は入れない | 「記録したのに検索で出てこない」が実際に起きたら |
| 本文の切り詰めは削減目的ではなく歯止め | — |

**着手すべき時期**: 案 1 の後。骨格の管理方法を確立する前に 2 つ目の MCP サーバーを
作ると、今度は「MCP サーバーが 2 箇所に分岐」が起きる。

## 4. サービスの生存確認

Workers の Cron から、運用しているサービスの `/health` を順に叩き、
応答が異常なら Discord へ通知する。

**根拠**: 現在 gamers-highlight（Vercel）、AgentFailures（Workers）、
Supabase 2 プロジェクトを運用しているが、停止に気づく手段があるのは
AgentFailures のみである。Supabase の無料プランは 7 日間アクセスが無いと
自動停止するが、対策しているのは片方だけである。

**規模**: 通知先（Discord）は既にあるため、1 ファイルで済む見込み。
