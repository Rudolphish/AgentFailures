# レビューチェックリスト（自動レビュー用）

このプロジェクト（AgentFailures）で守るべき不変条件。自動レビューはこのリストと
照らして差分をチェックする。

**本来ここに足すのは、一度やらかしたことだけ。** 現時点ではまだ運用実績が無いため、
要件定義（[`requirements.md`](./requirements.md)）から導いた「壊してはいけない約束」を
初期値として置いている。実際に事故が起きたら、その項目をここへ追記すること。

背景は [`CLAUDE.md`](../CLAUDE.md)（コードの落とし穴）と
[`lessons.md`](./lessons.md)（進め方の落とし穴）にある。

## 1. シークレット（最重要）

- [ ] `.env` / `.dev.vars` がコミットされていないか。`.gitignore` の該当行を消していないか
- [ ] `MCP_AUTH_TOKEN` の実値が、
      ソース・README・テストコード・コミットメッセージに書かれていないか
- [ ] `.env.example` に実値が入っていないか（プレースホルダのままか）
- [ ] **シークレットが増えていないか。** D1 移行で `MCP_AUTH_TOKEN` の 1 つだけになった。
      ストアへの接続情報は `wrangler.jsonc` の binding であり、秘密ではない。
      新たに接続文字列やキーを足す変更は、その必要性から疑う
      （`database_id` は識別子であり秘密ではない。これはコミットしてよい）

## 2. 認証

- [ ] `/mcp` への到達経路すべてで `isAuthorized` を通しているか。
      新しいパスやメソッドを足したとき、認証の前に処理を書いていないか
- [ ] トークン比較を `===` や `!==` による素の文字列比較に戻していないか
      （`src/auth.ts` の SHA-256 経由の定数時間比較を迂回していないか）
- [ ] エラーレスポンスにトークンや内部情報が混入していないか
      （D1 のエラーメッセージをそのまま返す経路が増えていないか。
      `store.ts` は例外を捕まえて文言を付け替えているが、元のメッセージを
      そのまま載せているため、SQL が漏れうる点は変わらない）
- [ ] `/health` が状態以外（件数・スキーマ・環境変数など）を返していないか

## 3. MCP ツール仕様

- [ ] ツールが `search_failures` と `record_failure` の 2 つだけか。
      スコープ外（削除・更新・分類・同期）のツールが増えていないか
- [ ] `search_failures` が上限件数を超えて返しうる経路が無いか。
      zod の `.max(5)` と `store.ts` の `Math.min` の**二重の防御を両方**維持しているか
- [ ] 既定件数 3 / 上限 5 の値を変えていないか
- [ ] 並びが**関連度の降順**（一致した語数 → 語の出現回数）→ `created_at` の降順
      になっているか。`created_at` のみへ戻していないか
      （戻すと、1 語で多数一致するクエリに対し関連の薄い新しい記録だけが返る）
- [ ] 出現回数の数え上げが `lower()` を通っているか
      （**`LIKE` は ASCII の大文字小文字を無視するが `replace()` は区別する。**
      通さないと `Cron` で引いたとき条件は一致するのに出現回数が 0 になる）
- [ ] 出現回数の `replace()` へ渡す語を `escapeLikePattern` に通していないか
      （`\` を足した文字列は `replace()` では一致しない）
- [ ] バインド値を WHERE → ORDER BY → LIMIT の順に積んでいるか
      （`?` の出現順と一致しなければ条件と並び順の値が入れ替わる）
- [ ] 一致総数を `limit` で切る前に数えているか。`records.length` を
      一致総数として応答に書いていないか
- [ ] `AND` が 0 件のときの `OR` への切り替えが、**語が 2 つ以上のときだけ**か。
      `OR` を既定にしていないか（実データで `キャッシュ 古い` が 22 件一致し、
      既定 limit 3 ではほとんど絞り込めない）
- [ ] `OR` へ広げたことを応答に明記しているか。`domain` / `environment` の
      絞り込みが `OR` に巻き込まれていないか（語の条件は括ること）
- [ ] `query` を**空白（半角・全角とも）で語に分割し、語ごとの `LIKE` を `AND`**
      で結合しているか。連結文字列への 1 回の部分一致へ戻していないか
      （戻すと `cron 曜日` のような複数語が原理的に 0 件になる。
      2026-11-20 まで実際にそうなっていた）
- [ ] 分割の区切りから全角空白 (U+3000) が落ちていないか
      （JavaScript の `\s` に含まれる。`/\s+/` を半角のみの表現へ変えていないか）
- [ ] 語数の上限を超えた分を**黙って捨てていないか。** 捨てた語数を応答に
      書いているか（`SearchResult.droppedTerms`）
- [ ] 各語を `escapeLikePattern` に通しているか。`ESCAPE '\'` の指定が
      語ごとの `LIKE` すべてに付いているか
- [ ] `record_failure` の必須項目
      （`domain` / `environment` / `attempted` / `observed` / `cause` /
      `cause_is_assumption` / `tags`）が required から外れていないか
- [ ] 必須項目が欠落した入力で、DB へ到達する前にエラーを返しているか
      （検証を通さず insert する経路が増えていないか）
- [ ] `record_failure` の説明文に
      「原因が推定である場合は cause_is_assumption を true にすること」が残っているか
- [ ] `observed` の説明から「観測された事実のみ」という指示が消えていないか

## 4. データベース（D1 / SQLite）

**2026-11-20 に Supabase (PostgreSQL) から D1 へ移行した。** 旧構成に向けた項目
（RLS・`pg_trgm`・`immutable` ラッパー関数）はこの節から外した。いずれも D1 には
存在しない仕掛けであり、残しておくと**無いものを探させることになる**。
Postgres 固有の罠そのものは `CLAUDE.md` の当時の節に記録がある。

- [ ] `failures` の必須列から `NOT NULL` または空文字を拒否する `CHECK` を外していないか
- [ ] 生成列 `search_text` を `STORED` から `VIRTUAL` へ変えていないか、
      連結する列を減らしていないか（`query` の検索対象がこの列である）
- [ ] `cause_is_assumption` を 0/1 以外で保存する経路、`tags` を JSON 配列の
      文字列以外で保存する経路が増えていないか。**SQLite に真偽値も配列も無いため、
      変換は `store.ts` の `toRecord` の 1 箇所に閉じている**
- [ ] `id` と `created_at` を SQL の既定値へ移していないか
      （`crypto.randomUUID()` と `toISOString()` を Worker 側で生成している。
      SQLite の `CURRENT_TIMESTAMP` は `YYYY-MM-DD HH:MM:SS` で ISO 8601 と異なり、
      既定値に頼ると経路によって書式が割れる）
- [ ] `LIKE` に `ESCAPE '\'` の指定が付いているか。`escapeLikePattern` を
      通さずにユーザー入力を `LIKE` へ渡す経路が増えていないか
- [ ] `created_at` と `domain` の索引を消していないか
- [ ] マイグレーションを破壊的に書き換えていないか
      （適用済みのファイルを編集するのではなく、新しいファイルを足す）
- [ ] `search_log` への記録が**失敗しても検索を返す**形を保っているか。
      `logSearch` の `catch` から `console.error` を消していないか
      （**記録の失敗は検索の応答に現れないため、声を上げなければ気づかれない**）
- [ ] keep-alive が `search_log` へ `source='writable-check'` の行を
      入れる処理を落としていないか。**これが無いと `search_log` が空のとき
      「誰も検索していない」と「記録が壊れている」を区別できない**
      （2026-10-13 に同じ形で 14 日間気づけなかった。失敗談 `5a236586`）
- [ ] `search_log` に失敗談の本文を保存する列を足していないか
      （`failures` との重複した保存を増やす意味が無い）
- [ ] `search_log` の `CHECK`（`source` ごとに列の要求を変える）を外していないか
- [ ] `wrangler.jsonc` の `migrations_dir` を `d1_databases[]` の外へ出していないか
      （**トップレベルに書くと警告 1 行だけで無視され、既定の `./migrations` を
      見に行く。** 2026-11-18 に実際に踏んだ）
- [ ] コネクタの `d1_database_query` で DDL を流したとき、`d1_migrations` への
      記録を省いていないか（省くと次の `migrations apply` が同じ SQL を再実行する）

## 5. Cloudflare Workers

- [ ] Node 固有 API（`process` / `Buffer` / `fs` 等）に依存するコードを足していないか
- [ ] リクエストを跨いで状態を保持していないか
      （Worker のインスタンスは使い回されるため、
      ユーザー単位・リクエスト単位の情報をモジュールスコープに置くと他リクエストへ漏れる）
- [ ] keep-alive の Cron Trigger（`wrangler.jsonc` の `triggers.crons`）を、
      **30 日の観測期間が終わる前に**消していないか。
      **D1 に自動停止は無いため、これは停止の回避策ではない。**
      残してある目的は 2 つで、(1)「D1 は停止しない」を観測で裏づけること、
      (2) `select max(ran_at)` で最後に書き込めた時刻が分かること。
      観測が済んだら、Cron・`keepalive_log`・`ping()`・本項目をまとめて落とす
- [ ] keep-alive を読み取りへ戻していないか。`keepalive_log` への追記であることに
      意味がある（**実行の有無が後から追える**。なお「アクティビティとして確実に
      数えられる」という Supabase 時代の狙いは、書き込みでも停止したため外れている）
- [ ] `scheduled` ハンドラの失敗を握りつぶしていないか（`console.error` まで消していないか）。
      疎通したが `keepalive_log` へ追記できなかった場合も `console.error` へ出ているか。
      **keep-alive は失敗しても誰も困らないため、自ら声を上げない実装は気づかれない**

## 出力フォーマット（自動レビューが従う形式）

レビュー結果は必ず最初の行に以下のいずれかを書くこと：

```
VERDICT: PASS
```
または
```
VERDICT: FAIL
```

FAIL の場合は、その後に箇条書きで具体的な修正指示を書くこと
（ファイルパスと直すべき内容を明記）。
