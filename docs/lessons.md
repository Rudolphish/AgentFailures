# 進め方の記録

このファイルは**開発の進め方**でやらかしたことを残す場所である。
セッション開始時にフック（`.claude/hooks/session-brief.mjs`）が全文を読み込ませる。

コードそのものの落とし穴は [`CLAUDE.md`](../CLAUDE.md) に、
レビューで見るべき不変条件は [`review-checklist.md`](./review-checklist.md) に書く。

## 書き方

- 「何が起きたか」を具体的に書く。「〜に注意」だけでは、次に読んだときに判断に使えない。
- 一度実際に起きたことだけを書く。起こりうる話は書かない。
- 8192 文字を超えたらフックが警告を出す。似た項目は統合して畳むこと。

---

## 検証していないものを「動く」と書かない

- **2026-09-08**: MCP サーバーの実装時、Worker から実際の Supabase への読み書きを
  一度も通していない状態だった。ダミーの URL を向けた検証しかしていないため、
  PostgREST 経由の `ilike` と `insert` が期待通り動くかは未確認である。
  完了報告では「未検証の部分」として明示した。
  検証できていない範囲は、成果報告のたびに名指しで書き出すこと。

## 外部サービスの料金・制限は記憶で答えない

- **2026-09-08**: 課金の有無を聞かれた際、Supabase と Cloudflare の料金体系を
  記憶から答えようとした。実際には Supabase 無料プランの「7 日間非アクティブで
  プロジェクトが自動停止する」という、金額ではなく可用性に関わる制約があり、
  これは設計（keep-alive Cron の追加）を変える要因だった。
  料金・上限・制限は必ず一次情報を引いて確認し、確認できなかった項目は
  「確認できなかった」と書く。実際に Cloudflare Workers 無料枠の
  1 日あたりリクエスト上限は公式ドキュメントに到達できず未確認のままである。

## 既定値を勝手に埋めず、仕様の解釈が割れる箇所は明示する

- **2026-09-08**: `tags` が必須項目か、空配列を許すかは要件から一意に決まらなかった。
  黙って決めるのではなく「必須キーだが空配列可」とした上で、判断が入った箇所として
  報告に列挙した。仕様の解釈が割れうる箇所は、実装した上で必ず表に出すこと。

## 手順書は、読み手の実行環境で通ることを確かめてから渡す

- **2026-09-08 / 09**: セットアップ手順書を Unix 系シェル前提で書いて渡したところ、
  Windows の PowerShell で実行され、`openssl` が存在せず手順 3-3 で止まった。
  その指摘を受けて付録に PowerShell の読み替えを追加したが、対象を手順 4 に
  限定したため、今度は手順 3-2 の `curl -sS` が
  `パラメーター名 'sS' に一致するパラメーターが見つかりません` で止まった。
  Windows PowerShell 5.1 では `curl` が `Invoke-WebRequest` の別名である。
  同じ原因で二度止めたことになる。
  一度環境差の問題が出たら、その場の一箇所を直すのではなく、
  文書全体を同じ観点で洗い直すこと。

## ローカルで動くことは、デプロイ先で動く保証にならない

- **2026-09-09**: MCP サーバーを `wrangler dev` で入念に確認し、`/health`・認証・
  ツール一覧・入力検証まで通ることを確かめたうえで完了として報告した。
  しかしデプロイ先では全リクエストが error 1101 で失敗した。原因は
  `fetch` ハンドラを非 async のメソッドとして書いていたことで、ローカルの
  workerd は許容するが、デプロイ先は
  `TypeError: Callback returned incorrect type; expected 'Promise'` を投げる。
  ローカルでの確認は、デプロイ先での確認の代わりにはならない。

## 原因が絞れないうちに手を動かさず、まずログを出させる

- **2026-09-09**: 上記の 1101 を調査した際、ajv の実行時コード生成、
  バンドルサイズ、起動時間などを次々と疑った。いずれも外れであり、
  実際には `wrangler tail` のログ 1 行で原因の範囲が即座に確定した
  （リクエスト時の例外であり、モジュール読み込みの問題ではないと分かった）。
  観測手段があるなら、推測を重ねる前にそれを使うこと。

## 例外を握り潰す実装は、障害時に何も残さない

- **2026-09-09**: 上記の調査が難航した理由の一つは、ハンドラに try/catch が無く、
  例外が Cloudflare の 1101 エラーページになって内容が失われていたことである。
  捕捉して `console.error` へ出すだけで、次からは具体的な内容がログに残る。
  外部に公開する入口には、必ず捕捉と記録を置くこと。

## 文字化けは「成功したまま壊れる」ため、疎通確認の合否条件に含める

- **2026-09-09**: PowerShell から `Invoke-RestMethod` で日本語を含む失敗談を
  登録したところ、要求は成功したが、保存された値が文字化けしていた。
  Windows PowerShell 5.1 は `-Body` に文字列を渡すと UTF-8 以外で送信する。
  `[System.Text.Encoding]::UTF8.GetBytes()` でバイト列にして渡せば起きない。
  問題は、**要求が成功として返るため、応答本文を読むまで気づけない**ことである。
  手順書の「完了の判定」を「登録された内容が返ること」で済ませていたのが誤りで、
  返ってきた文字列そのものを確認させる必要があった。
  日本語を扱う経路では、疎通確認の合否条件に往復後の文字列の一致を必ず含めること。
- **2026-09-09（続き）**: 上記を修正したところ、今度は別の化け方（`縺` `繝` `繧`
  が並ぶ）が現れた。原因は送信ではなく、`.ps1` ファイルが BOM の無い UTF-8 で
  保存されており、Windows PowerShell 5.1 がこれを CP932 として読んでいたことである。
  **文字列がプログラムへ渡るまでの経路は複数あり、一箇所直しても別の箇所が残る。**
  文字化けは化け方から原因を判別できる（`?` の並びは送信時の非可逆変換、
  漢字の並びは復号したバイト列の解釈違い）ため、症状と原因の対応を
  手順書に残して切り分けられるようにした。
