# 進め方の記録

このファイルは**開発の進め方**でやらかしたことを残す場所である。
セッション開始時にフック（`.claude/hooks/session-brief.mjs`）が全文を読み込ませる。

コードそのものの落とし穴は [`CLAUDE.md`](../CLAUDE.md) に、
レビューで見るべき不変条件は [`review-checklist.md`](./review-checklist.md) に書く。

## 書き方

- 「何が起きたか」を具体的に書く。「〜に注意」だけでは、次に読んだときに判断に使えない。
- 一度実際に起きたことだけを書く。起こりうる話は書かない。
- 8192 文字を超えたらフックが警告を出す。似た項目は統合して畳むこと。

## 検証していないものを「動く」と書かない

- **2026-09-08**: MCP サーバーの実装時、Worker から実際の Supabase への読み書きを
  一度も通していない状態だった。ダミーの URL を向けた検証しかしていないため、
  PostgREST 経由の `ilike` と `insert` が期待通り動くかは未確認である。
  完了報告では「未検証の部分」として明示した。
  検証できていない範囲は、成果報告のたびに名指しで書き出すこと。

## 外部サービスの料金・制限は記憶で答えない

- **2026-09-08**: 課金の有無を聞かれた際、Supabase と Cloudflare の料金体系を
  記憶から答えようとした。実際には Supabase 無料プランの「7 日間非アクティブで
  プロジェクトが自動停止する」という、金額ではなく可用性に関わる制約があり、
  これは設計（keep-alive Cron の追加）を変える要因だった。
  料金・上限・制限は必ず一次情報を引いて確認し、確認できなかった項目は
  「確認できなかった」と書く。実際に Cloudflare Workers 無料枠の
  1 日あたりリクエスト上限は公式ドキュメントに到達できず未確認のままである。

## 既定値を勝手に埋めず、仕様の解釈が割れる箇所は明示する

- **2026-09-08**: `tags` が必須項目か、空配列を許すかは要件から一意に決まらなかった。
  黙って決めるのではなく「必須キーだが空配列可」とした上で、判断が入った箇所として
  報告に列挙した。仕様の解釈が割れうる箇所は、実装した上で必ず表に出すこと。

## 手順書は、読み手の実行環境で通ることを確かめてから渡す

- **2026-09-08 / 09**: セットアップ手順書を Unix 系シェル前提で書いて渡したところ、
  Windows の PowerShell で実行され、`openssl` が存在せず手順 3-3 で止まった。
  その指摘を受けて付録に PowerShell の読み替えを追加したが、対象を手順 4 に
  限定したため、今度は手順 3-2 の `curl -sS` が
  `パラメーター名 'sS' に一致するパラメーターが見つかりません` で止まった。
  Windows PowerShell 5.1 では `curl` が `Invoke-WebRequest` の別名である。
  同じ原因で二度止めたことになる。
  一度環境差の問題が出たら、その場の一箇所を直すのではなく、
  文書全体を同じ観点で洗い直すこと。

## ローカルで動くことは、デプロイ先で動く保証にならない

- **2026-09-09**: MCP サーバーを `wrangler dev` で入念に確認し、`/health`・認証・
  ツール一覧・入力検証まで通ることを確かめたうえで完了として報告した。
  しかしデプロイ先では全リクエストが error 1101 で失敗した。原因は
  `fetch` ハンドラを非 async のメソッドとして書いていたことで、ローカルの
  workerd は許容するが、デプロイ先は
  `TypeError: Callback returned incorrect type; expected 'Promise'` を投げる。
  ローカルでの確認は、デプロイ先での確認の代わりにはならない。

## 原因が絞れないうちに手を動かさず、まずログを出させる

- **2026-09-09**: 上記の 1101 を調査した際、ajv の実行時コード生成、
  バンドルサイズ、起動時間などを次々と疑った。いずれも外れであり、
  実際には `wrangler tail` のログ 1 行で原因の範囲が即座に確定した
  （リクエスト時の例外であり、モジュール読み込みの問題ではないと分かった）。
  観測手段があるなら、推測を重ねる前にそれを使うこと。

## 例外を握り潰す実装は、障害時に何も残さない

- **2026-09-09**: 上記の調査が難航した理由の一つは、ハンドラに try/catch が無く、
  例外が Cloudflare の 1101 エラーページになって内容が失われていたことである。
  捕捉して `console.error` へ出すだけで、次からは具体的な内容がログに残る。
  外部に公開する入口には、必ず捕捉と記録を置くこと。

## 文字化けは「成功したまま壊れる」ため、疎通確認の合否条件に含める

- **2026-09-09**: PowerShell から `Invoke-RestMethod` で日本語を含む失敗談を
  登録したところ、要求は成功したが、保存された値が文字化けしていた。
  Windows PowerShell 5.1 は `-Body` に文字列を渡すと UTF-8 以外で送信する。
  `[System.Text.Encoding]::UTF8.GetBytes()` でバイト列にして渡せば起きない。
  問題は、**要求が成功として返るため、応答本文を読むまで気づけない**ことである。
  手順書の「完了の判定」を「登録された内容が返ること」で済ませていたのが誤りで、
  返ってきた文字列そのものを確認させる必要があった。
  日本語を扱う経路では、疎通確認の合否条件に往復後の文字列の一致を必ず含めること。
- **2026-09-09（続き）**: 上記を修正したところ、今度は別の化け方（`縺` `繝` `繧`
  が並ぶ）が現れた。原因は送信ではなく、`.ps1` ファイルが BOM の無い UTF-8 で
  保存されており、Windows PowerShell 5.1 がこれを CP932 として読んでいたことである。
  **文字列がプログラムへ渡るまでの経路は複数あり、一箇所直しても別の箇所が残る。**
  文字化けは化け方から原因を判別できる（`?` の並びは送信時の非可逆変換、
  漢字の並びは復号したバイト列の解釈違い）ため、症状と原因の対応を
  手順書に残して切り分けられるようにした。

## 分量や性能は体感で語らず、直す前に測る

- **2026-09-10**: 検索結果が「1回で5000文字を超えていて重い」と報告し、本文を
  切り詰める改修に着手した。実測すると 5 件で 4263 文字であり、しかも各項目の
  中央値は 85〜115 文字と一様に中程度で、切り詰めても削減は 3% にとどまった。
  最初に入れた上限は緩すぎて逆に出力が 1% 増えた（省略の注意書きの分）。
  **数字を出さずに問題の大きさを断定し、その断定に基づいて設計してしまった。**
  分量・性能の問題は、直す前に測ること。測ってから対策を選べば、
  そもそも切り詰めが有効な形の問題ではないと分かったはずである。
  なお改修自体は無駄ではなく、見出しを attempted から observed + cause へ
  変えた部分は有効であり、上限も 1 項目 4000 文字まで許すスキーマに対する
  歯止めとして機能する（実測で 81424 文字が 4694 文字に収まる）。

## 対策は、それが動いたことを後から確認できる形で入れる

- **2026-09-27**: Supabase の自動停止を避けるため keep-alive Cron を週 2 回
  設定していたが、それでもプロジェクトが停止した。気づいたのは 17 日後、
  ユーザーが使おうとして繋がらなかったときである。
  問題は停止そのものより調査ができなかったことで、keep-alive が読み取りクエリ
  だけだったため、**Cron が実行されたのかどうかを確かめる手段が DB 側に無かった。**
  Cloudflare のログへは（プロキシに阻まれて）到達できず、切り分けはそこで止まった。
  対策を入れるときは、その対策が動いたことを後から確認できる形にすること。
  keep-alive を `keepalive_log` への追記に変えたのはこのためで、停止の回避と
  同時に `select max(ran_at)` で最後の成功時刻が分かる。
  なお同じ盲点は `review-status.mjs` で一度解決済みだった
  （フックが走らなかったことが見えない問題）。既に持っている解法を
  別の場所へ適用できていない。

## ソースを読んだからといって、読んだ層が正しいとは限らない

- **2026-10-16**: keep-alive の Cron が設定と違う曜日に発火していた。曜日の
  番号付けを疑い、公式ドキュメントへ到達できなかったため Cloudflare 自身の
  cron パーサ `cloudflare/saffron` のソースを読んだ。`lib.rs` の
  `byte_to_weekday` に `0 => Sun, 1 => Mon, 4 => Thu` とあったため
  「設定は月・木で正しく、ドキュメントの記述は合っている」と報告した。
  **これが誤りだった。** その関数はパース後に -1 された内部表現を曜日へ戻す
  ものであり、入力の番号付けではない。入力を解釈しているのは `parse.rs` の
  `dow_expr` で、そのテストは `SUN=1 / MON=2 / WED=4` を示していた。
  つまり 1 始まりの Quartz 方式であり、`1,4` は日曜と水曜である。
  ダッシュボードの表示（At 03:00 AM on Sunday and Wednesday）が実測と
  一致しており、こちらが正しかった。
  **「一次情報を読んだ」は、読む層を間違えていれば推測より質が悪い。**
  断定の強さが上がるぶん、誤りが検証されにくくなる。
  入出力の境界を扱う値は、内部表現ではなく入力を解釈している箇所を読むこと。
  そして**観測値と食い違ったときは、観測値の側を疑う前に自分の読みを疑う。**
  今回は「水曜に発火し木曜に発火しない」という観測が最初から答えを示していた。

## 風化を防ぐ仕組みを、手作業の後ろに置かない

- **2026-10-16**: 自動レビュー機構を作った際、フック定義の `.claude/settings.json`
  だけはリポジトリに含めず、`docs/claude-settings.example.json` を手でコピーして
  もらう手順にした。**5 週間コピーされないままで、その間レビューは一度も自動実行
  されていなかった。** 毎回こちらが手で起動していたぶんだけが動いていた。
  皮肉なことに `session-brief.mjs` の冒頭には「手で書きに行く前提のものは例外なく
  風化する。だから読ませる側を仕組みにする」と書いてある。
  **その仕組みの有効化自体を手作業にしていた。**
  設定ファイルを追跡対象に変え、clone した時点で効くようにした。
  手作業を残すなら、それが済んだかどうかを次の着手時に必ず検証すること。
  渡したまま確認しない作業は、やられていないものとして扱う。

## 検査ツールは、相手が固定しているバージョンで走らせる

- **2026-10-29**: 規則の配布先を LearnAI へ広げた際、挿入した `CLAUDE.md` が
  `prettier --check` を通ることを `npx prettier@3.3.3` で確認し、通ったので push した。
  **CI は落ちた。** そのリポジトリは `package-lock.json` で prettier 3.9.9 を解決しており、
  3.3.3 は刻印コメントの次の空行だけを要求するのに対し、3.9.9 は終了マーカーの前の
  空行も要求する。整形規則はバージョンで変わる。
  `npm ci` を済ませてリポジトリの固定バイナリで `npm run format:check` を流せば、
  push 前に同じ失敗を再現できた（実際に直した後はそれで確認した）。
  **「手元で通った」は、同じ名前の別バージョンで通ったにすぎないことがある。**
  検査を他人のリポジトリで満たす必要があるときは、まずそのリポジトリが
  何を固定しているかを読む。
- なお基準線（変更前のファイルが検査を通ること）は先に取っていたため、
  「元から落ちていたのか自分が落としたのか」の切り分けでは迷わなかった。
  **基準線は役に立ったが、バージョンを揃えていなければ基準線ごと間違える。**

## 実装を変えた diff の中で、同じ文書の「古い説明」を消し忘れる

- **2026-10-29 / 10-30**: 2 回続けて同じ形でレビューに落ちた。
  10-29 は刻印を `synced=` から `updated=` に変えたのに、`docs/rules.md` に
  `synced=` 前提の記述と「別の監視を用意しなくてよい」が残っていた。
  10-30 はブランチ名を `日付-source` に変え force push をやめたのに、
  `docs/rules-distribution.md` の同じ節の末尾に
  「同じ日に 2 回走った場合は、同じブランチへ上書きして既存の PR を更新する
  （`git switch -c` のままでは既存ブランチで落ちた）」という旧方式の説明が残り、
  **12 行前の記述と正反対になっていた。**
  いずれも**自分が直前に書いた文**で、どちらも配布先が写して使う手順書である。
- 共通の原因は、**節の前半だけを書き換えて、後半を読み直していない**こと。
  新しい説明を「足す」と、古い説明は目に入らない位置へ押し下げられる。
  差分レビューでも、変更行の近傍しか見ないため気づかない。
- **対策: 挙動を変えたら、その挙動に言及している箇所を文書全体で grep する。**
  今回なら `switch -c` / `force` / `ブランチ名` / `日付` で引けば全部出た
  （実際、直した後に `grep -n 'git switch'` で残存 1 件を確認している）。
  diff を見るのではなく、**変えた概念の名前で引く。**
