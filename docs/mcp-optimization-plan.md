# MCP の最適化計画

`search_failures` / `record_failure` の改善計画。**意味検索の導入は含まない**
（理由は §2）。

計測はすべて 2026-11-13 時点の実データ（`failures` 134 行、`search_text` 合計
104,928 文字、1 行平均 783 文字、最大 1,887 文字）に対して行った。

D1 への移行計画は [`d1-migration-plan.md`](d1-migration-plan.md) にあり、
**本書の段階分けはその移行と噛み合わせてある**（§5）。

---

## 1. 結論

検索の取りこぼしは起きている。ただし原因は索引や埋め込みではなく、
**クエリの組み立てと結果の伝え方にある。** 4 件の欠陥を測って特定した。

| # | 欠陥 | 深刻度 | 直す段階 |
| --- | --- | --- | --- |
| 1 | **複数語のクエリが必ず 0 件になる** | 高 | Phase 1 |
| 2 | 「該当 N 件」が一致数ではなく返却数である | 高 | Phase 1 |
| 3 | `domain` の値の列挙が古い（7 / 32） | 中 | Phase 0 |
| 4 | 並びが新しい順のみで、関連度が無い | 中 | Phase 1 |

いずれも**数十行の範囲**で直る。意味検索（数百行＋外部依存）より先に行う。

## 2. 意味検索を入れない理由

別途測った結果を要約する。詳細は `docs/ideas.md` の案 5 と移行計画 §7.5。

- **語彙ギャップは実在する。** `プロセスを止める` は 0 件だが `pkill` なら 7 件、
  `スケジュール実行` は 0 件だが `cron` なら 10 件一致する
- **しかし再発の原因はそこではなかった。** `再発` / `記録済み` を含む記録 4 件の
  `cause` を読むと、3 件は「CLAUDE.md または `docs/lessons.md` に書いてあり、
  セッション開始時にコンテキストへ載っていたのに適用しなかった」、1 件は
  「検索を怠った」である。**「検索したが出てこなかった」は 1 件も無い**
- **規模が足りない。** `domain + observed + cause` の全件が 48,046 文字、
  各 70 字へ切れば 19,729 文字である。索く必要そのものを無くせる量であり、
  意味検索が要るのは渡しきれなくなってからである

**呼ばれていないツールのランキングを改善しても効果は出ない。** これは
`docs/lessons.md` の「分量や性能は体感で語らず、直す前に測る」と同じ形の誤りを
避けるための判断である。

見直す条件は §7 に書く。

## 3. 欠陥の内容と直し方

### 欠陥 1: 複数語のクエリが必ず 0 件になる

`src/store.ts:55` は `query` を**連結文字列への 1 回の部分一致**に渡している。

```ts
request = request.ilike('search_text', `%${escapeLikePattern(input.query)}%`);
```

`search_text` は `domain` から `tags` までを空白で連結した 1 本の文字列である。
したがって `cron 曜日` は「`cron 曜日` という連続した文字列」を探すことになり、
**語がその順で隣接していない限り一致しない。**

実測（`search_text` に対する直接のクエリ）:

| クエリ | 現在（部分一致） | 語ごとの AND | 語ごとの OR |
| --- | --- | --- | --- |
| `cron 曜日` | **0 件** | 1 件 | 10 件 |
| `曜日 cron` | **0 件** | 1 件 | 10 件 |
| `pkill シェル` | **0 件** | 6 件 | 11 件 |
| `キャッシュ 古い` | **0 件** | 3 件 | 22 件 |

**4 例すべてで 0 件である。** エージェントが自然に打つ複数語のクエリは、
現在の実装では原理的に当たらない。

**直し方**: `query` を空白で分割し、語ごとに条件を重ねる。

- **AND を既定にする。** OR は `キャッシュ 古い` で 22 件（全体の 16%）一致し、
  既定 limit 3 では「新しい順の 3 件」が返るだけで関連度が無い。欠陥 4 と
  複合して悪化する
- **AND が 0 件のときは OR へ落とし、一致語数で並べる。** 段階を 2 つに
  することで、絞りすぎと広すぎの双方を避ける
- **区切りは半角空白と全角空白（U+3000）の両方。** 日本語入力では U+3000 が
  来る。これは**未検証**なので §6 の検証項目に入れる
- 語数の上限を置く（例: 8 語）。PostgREST / D1 いずれもクエリが長くなる

### 欠陥 2: 「該当 N 件」が一致数ではなく返却数である

`src/format.ts:116`:

```ts
`該当 ${records.length} 件（新しい順）。`
```

`records` は **limit で切った後の配列**である。`キャッシュ` は 10 件一致するが、
既定 limit が 3（`src/schema.ts:4`）なので応答は「該当 3 件」と書く。

**これは誤った情報である。** 読んだエージェントは「3 件しかない」と理解し、
`limit` を上げる理由を与えられない。7 件が見えないまま終わる。

0 件のときも同じ問題がある。`src/format.ts:106` は
「該当する失敗談はありません。」と書くが、正確には
**「この文字列を含む記録が無い」**でしかなく、欠陥 1 のもとでは
複数語のクエリを打つたびにこの文が返る。「記録が無い」と読めてしまう。

**直し方**: 一致総数を別に取得し、`一致 10 件中 3 件を表示（新しい順）` の形にする。
0 件のときは「一致する記録はありません（query は語ごとの AND で判定している）」
のように、**判定方法を添える。**

- Supabase: `select` に `{ count: 'exact', head: true }` を付けた別リクエスト
- D1: 同じ `WHERE` に対する `COUNT(*)`（`batch()` で 1 往復に収められる）

### 欠陥 3: `domain` の値の列挙が古い

`src/schema.ts` の `domain` の説明文は「現在使われている値」として 7 個を挙げる。

```
nextjs / cloudflare-workers / supabase / github-actions / claude-code /
windows-powershell / discord-api
```

**実際には 32 個ある。** 件数の多い順に:

| domain | 件数 | 説明文に載っているか |
| --- | --- | --- |
| `claude-code` | 42 | ○ |
| `nextjs` | 25 | ○ |
| `github-actions` | 9 | ○ |
| **`playwright`** | 7 | **×** |
| **`prisma`** | 6 | **×** |
| `discord-api` | 5 | ○ |
| `supabase` | 5 | ○ |
| **`react`** / **`learnai`** | 3 / 3 | **×** |
| 他 24 種 | 1〜2 | **×** |

`domain` は**完全一致**（`src/store.ts:49` の `.eq()`）である。列挙に無い値を
知らないエージェントは、`domain` を使わないか、載っている値から誤って選んで
0 件を引く。`playwright` の 7 件は列挙だけを見ていると到達できない。

**直し方**: **列挙をやめる。** 32 個を書き並べるのは説明文を肥大させ、しかも
また古くなる。`docs/lessons.md` の「手で書きに行く前提のものは例外なく風化する」が
そのまま当てはまる。

- 説明文を「完全一致で判定する。**値が不確かな場合は domain を省略し、
  query だけで検索すること。**」に変える
- 件数上位 3 つ（`claude-code` / `nextjs` / `github-actions`、合計 76 件で全体の
  57%）のみ例として残す
- 動的に `distinct domain` を引く案は採らない。ステートレス構成のため
  リクエストごとにクエリが 1 本増え、得るものが説明文の鮮度だけである

### 欠陥 4: 並びが新しい順のみで、関連度が無い

`src/store.ts:45` は `created_at desc` のみで並べる。`キャッシュ` の 10 件に
対して返るのは**新しい 3 件**であり、最も関連する記録が古ければ出ない。

**直し方**: 一致語数の降順 → `created_at desc` の順に並べる。語ごとの一致は
欠陥 1 の修正で既に条件として持っているため、`CASE WHEN ... THEN 1 ELSE 0 END`
の和で安く作れる。

**日付の降順を第 2 キーとして残す。** 「結果は新しい順に返る」は現在の
ツール説明にある約束であり、同じ関連度なら新しいものが先にくる形を保つ。

## 4. 計測の土台（これを最初に入れる）

**現在、検索が呼ばれたかどうかも、0 件で返ったかどうかも記録されていない。**
`docs/lessons.md` の 2026-09-27 と同じ形である（keep-alive が動いたかを
確かめる手段が無く、切り分けがそこで止まった）。

`search_log` を 1 本足す。

| 列 | 内容 |
| --- | --- |
| `ran_at` | 実行時刻 |
| `query` / `domain` / `environment` | 受け取った入力（**本文は保存しない**） |
| `limit_value` | 要求された件数 |
| `matched_count` | 一致総数（欠陥 2 の修正で取得するもの） |
| `returned_count` | 実際に返した件数 |

- **記録に失敗しても検索は返す。** 計測のために本体を落とさない
- 入力のクエリ文字列は記録するが、**記録の本文は入れない**。重複した保存を
  増やす意味が無い
- これが無いと §7 の判定ができない。**順序としてこれを先に入れる**

## 5. 段階分けと、その順にする理由

**ストレージに依存するかどうかで切る。** D1 移行で `store.ts` の
クエリ組み立ては全面的に書き直しになるため、そこへ手を入れる改修を
Supabase 上で先に行うと**同じ作業を 2 回書く**ことになる。

| 段階 | 内容 | ストレージ依存 | 見込み |
| --- | --- | --- | --- |
| **Phase 0**（すぐ） | 欠陥 3（説明文）、欠陥 2 の**文言のみ**（0 件メッセージ、「表示」の語） | **しない** | 1 時間 |
| **Phase 1**（D1 移行と同時） | 欠陥 1・2・4、`search_log` | する | 3〜4 時間 |
| **Phase 2**（移行後 30 日） | 同義語の展開、全件ダイジェスト、意味検索の再判断 | — | 計測後に決める |

Phase 0 は `src/schema.ts` と `src/format.ts` の文言だけであり、移行しても
そのまま残る。Phase 1 は SQL を書く回に 1 回で入れる。

### この順にしないほうがよい条件

**欠陥 1 は深刻であり、放置の代価が大きい。** D1 移行に着手しない判断をした
場合、または**着手が 2 週間以上先になる場合は、Phase 1 を Supabase 上で先に
実施する。** 書き直しの重複（1〜2 時間）を払っても、複数語クエリが全滅して
いる状態を続けるほうが高い。

### Phase 2 の候補（まだ決めない）

- **同義語の展開**: 実測で 0 件だった対（`プロセス`→`pkill`、`スケジュール`→`cron`、
  `古い結果`→`キャッシュ`、`エンコーディング`→`文字化け`）のみを数行の表で持つ。
  Phase 1 の OR 分割が入ると効果が重複する可能性があるため、**先に計測を見る**
- **全件ダイジェスト**: 19,729 文字（各項目 70 字）を 1 ツールで返す案。
  「検索を呼ばない」問題への対策になるが、**サーバー側だけでは解決しない**
  （呼ばれなければ同じである）。CLAUDE.md の規則とフックの領分と重なるため、
  この計画の外で扱う
- **意味検索**: §7 の条件に当たったときのみ

## 6. 検証すること

`CLAUDE.md` の規則に従い、**わざと壊して落ちることを確認してから**信頼する。

| # | 確認すること | 方法 | 壊して確かめること |
| --- | --- | --- | --- |
| 1 | 全角空白（U+3000）で区切られたクエリが分割されるか | `cron　曜日`（全角）で引く | 分割を半角のみに戻すと 0 件に戻ること |
| 2 | 複数語の AND が効くか | `cron 曜日` が修正前 0 件 → 修正後 1 件 | **修正前の 0 件を先に記録する。** 基準線を取らないと「元から出ていたのか」が分からない |
| 3 | 一致数が返却数と別であるか | `キャッシュ` で「一致 10 件中 3 件」 | 期待値を 9 に書き換えて落ちること（10 と偶然一致していないか） |
| 4 | 一致語数の並びが効くか | 古い記録にしか無い語を含む 2 語で引く | 並びを日付のみに戻すとその記録が消えること |
| 5 | `search_log` が実際に書かれるか | 検索を 1 回流して `count(*)` の増分を見る | **件数とタイムスタンプで確認する。** 例外が出ないことは成功の証拠にならない |
| 6 | `search_log` の失敗が検索を落とさないか | テーブル名を誤った状態で検索する | 検索が通常どおり返り、ログに理由が出ること |
| 7 | 既存の単語クエリが壊れていないか | `pkill`（7 件）/ `キャッシュ`（10 件）/ `cron`（10 件） | 修正前の件数を先に記録し、一致すること |

**7 を省かない。** 欠陥 1 の修正はクエリの組み立てを変えるため、
単語 1 語の既存の経路を壊す余地がある。

## 7. 効果の判定条件と、意味検索を見直す条件

`search_log` が 30 日たまった時点で見る。

| 見るもの | 判定 |
| --- | --- |
| 0 件で返った検索の割合 | Phase 1 の前後で下がっていること |
| 0 件だった検索のクエリ | **実際には該当する記録があったものが何件あるか。** 1 件ずつ手で確かめる |
| `matched_count` が `limit` を超えた割合 | 高ければ既定 limit 3 の見直し（現在は上限 5） |

**意味検索を入れる条件を、これで初めて判定可能にする。**

現在の決定ログの文言は「記録したのに検索で出てこないが実際に起きたら」だが、
**起きても気づく手段が無い。** 次のとおり具体化する。

> `search_log` において、**0 件で返った検索のうち、実際には該当する記録が
> 存在していたものが 30 日で 5 件以上**あり、かつそれが Phase 1 の AND/OR 分割と
> 同義語の展開では救えない（語の重なりが無い）場合に、意味検索を検討する。
