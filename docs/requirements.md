# AgentFailures 要件定義

最終更新: 2026-09-08

## 1. 目的

自身が運用する AI エージェント群が「失敗談」を蓄積・参照するためのナレッジストア、
および当該ストアを読み書きするリモート MCP サーバーを構築する。

エージェントはタスク実行前に該当する失敗談を参照し、実行計画へ反映することを想定する。
本フェーズの目的は最小構成を稼働させ、実データを蓄積したうえで要件を検証することにある。

## 2. 設計方針

- 書き込みはエージェントのみが行い、閲覧は人間も行う。したがって保存形式は人間可読であること。
- 成功事例ではなく失敗事例を蓄積対象とする。
- PC・スマートフォン双方のクライアントから参照するため、ローカル常駐型ではなくホスト型とする。

## 3. 技術スタック

本項は確定事項であり、代替案の検討は行わない。

| 区分 | 採用技術 |
| --- | --- |
| ストア | **Cloudflare D1 (SQLite)**（2026-11-20 に Supabase から移行） |
| MCP サーバー | TypeScript / Cloudflare Workers / Streamable HTTP |
| SDK | `@modelcontextprotocol/sdk` |
| デプロイ | main への push で GitHub Actions が実行（`/health` の確認まで） |

**ストアの変更は確定事項の変更にあたる。** 当初 Supabase を確定としていたが、
無料プランの自動停止を 4 回踏み、keep-alive では回避できないと実測で分かったため
移行した。経緯と判断は [`d1-migration-plan.md`](d1-migration-plan.md) にある。
**MCP の境界（ツール 2 つ・固定トークン）は変えていないため、利用側への影響は無い。**

## 4. データスキーマ

以下を必須項目とする。

| 項目 | 型 | 説明 |
| --- | --- | --- |
| `id` | uuid | 主キー |
| `created_at` | timestamptz | 登録日時 |
| `domain` | text | 対象領域（例: `app-dev`, `notion-integration`, `scheduling`） |
| `environment` | text | 実行環境およびバージョン情報 |
| `attempted` | text | 何をしようとしたか |
| `observed` | text | 実際に何が起きたか。観測された事実のみを記載する |
| `cause` | text | 原因 |
| `cause_is_assumption` | boolean | 原因が推定である場合は `true` |
| `workaround` | text | 回避策（任意） |
| `tags` | text[] | タグ |

## 5. MCP ツール仕様

実装対象は以下の 2 ツールに限定する。

### 5.1 `search_failures`

- 入力
  - `domain`（任意）
  - `environment`（任意）
  - `query`（任意・全文検索）
  - `limit`（既定 3・最大 5）
- 出力
  - 該当する失敗談を新しい順に返却する。
  - 上限件数を超えて返却しないこと。

### 5.2 `record_failure`

- 入力: 第 4 章の必須項目。
- 必須項目が欠落している場合はエラーを返し、登録を行わないこと。
- ツール説明文に「原因が推定である場合は `cause_is_assumption` を `true` にすること」を明記すること。

## 6. 認証

環境変数に格納した固定トークンを HTTP ヘッダで照合する方式とする。OAuth は実装しない。

## 7. 可用性に関する追加要件

**2026-11-20 の D1 移行により、この要件の前提は解消した。**

### 解消した問題（2026-09〜2026-11）

Supabase の無料プランは、**7 日以上にわたり「十分な活動量」（sufficient activity）が
無い**場合にプロジェクトを自動停止する。**判定基準は活動の量であり、アクセスの
間隔ではない。** 週 2 回・1 行ずつの keep-alive ではこの基準を満たせず、
2026-09-27 / 10-13 / 10-29 / 11-11 の計 4 回停止し、そのつど人が復旧した。

Cloudflare D1 は使った分のみの課金であり、**公式ドキュメントに非アクティブ停止の
記述が無い**。これが移行の動機である。

### 現在の keep-alive の位置づけ

Cron Trigger による `keepalive_log` への 1 行追記は**残してある**。ただし
**停止の回避策ではない。**

- 実行間隔: 毎週日曜・水曜 03:00 UTC
  - 設定値は `0 3 * * 1,4`。Cloudflare の cron は曜日を 1 始まりで数え、
    1 が日曜であるため、この式は日曜と水曜を指す（詳細は `wrangler.jsonc` の注釈）
- 残す理由 1: **「D1 は停止しない」を文書で確認できていない**ため、30 日は観測で裏を取る
- 残す理由 2: `select max(ran_at) from keepalive_log` で「最後に書き込めたのはいつか」が
  分かり、障害時の切り分けに使える

**30 日の観測後、停止が起きなければ削除する**（移行計画 §6）。

## 8. スコープ外

以下は将来的な拡張候補であり、本フェーズでは実装しない。先回りした実装も行わない。

- Notion 連携・同期
- ベクトル検索 / pgvector
- カテゴリの自動分類、審査エージェント、削除機構
- 管理用 UI

## 9. 進め方

**これは 2026-09 の初期構築の手順であり、完了済みの記録である。**
手順 2 の「Supabase のマイグレーション」は当時のストアを指す。
現在のストアは D1 で、マイグレーションは `d1/migrations/` にある。

1. ディレクトリ構成と実装方針を提示し、着手前に確認を取る。
2. Supabase のマイグレーションを作成する。
3. MCP サーバーを実装する。
4. ローカルでの動作確認手順、およびデプロイ手順を提示する。
5. 疎通確認用の curl コマンド、および MCP クライアントの設定例を提示する。

## 10. 運用上の制約

- `.env.example` を用意し、シークレットはコミットしない。
- セットアップ手順は README に記載する。
